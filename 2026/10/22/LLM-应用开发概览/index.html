LLM 应用开发概览

1. 什么是 LLM 应用开发？

LLM 应用开发，是把大语言模型（Large Language Model, LLM）的语言理解与生成能力接入产品和业务流程。应用通常不只是“调用模型回答问题”，还要处理用户输入、业务数据、工具调用、安全控制和结果验证。

LLM 擅长处理自然语言、总结、分类、抽取和生成，但不一定擅长精确计算、保证事实正确或独立完成所有业务操作。因此，实际应用通常把模型与数据库、搜索、业务 API 和程序逻辑结合起来。

2. Prompt Engineering

**Prompt Engineering（提示词工程）**是设计模型输入的过程，让模型更准确、稳定地完成任务。

Prompt 通常可以包含：

  • 角色或任务：说明模型要做什么。
  • 背景和上下文：提供任务所需信息。
  • 约束：限定回答范围、格式或语气。
  • 示例：展示期望的输入与输出。
  • 输出格式：要求模型返回文本、JSON 或其他结构化内容。

例如，客服分类任务可以要求模型判断用户留言属于“退款、物流、商品咨询或其他”，并以固定 JSON 格式返回类别和理由。

Prompt 能改善模型表现，但无法完全消除幻觉或保证输出正确。对重要结果还需要校验、规则约束或人工审核。

3. RAG：检索增强生成

**RAG（Retrieval-Augmented Generation，检索增强生成）**让模型在回答前先从外部资料中检索相关内容，再根据检索结果生成答案。

RAG 适合回答模型训练时可能没有包含、或经常变化的内容，例如公司制度、产品文档和内部知识库。

常见处理流程

  1. 收集文档并清洗格式。
  2. 将文档切成较小片段（chunks）。
  3. 为片段生成向量表示（embeddings）。
  4. 将向量和原文存入检索系统。
  5. 用户提问时检索相关片段。
  6. 将问题和片段一起交给 LLM 回答。
  7. 根据需要返回引用来源或进行结果校验。

RAG 的优势与挑战

优势：

  • 可以使用外部或较新的资料。
  • 不必为了每次知识更新都重新训练模型。
  • 可以提供引用依据，方便用户核查。

挑战：

  • 检索不到正确资料时，回答仍可能不可靠。
  • 文档切分、检索质量和上下文长度都会影响结果。
  • 需要考虑资料权限、更新和删除机制。

4. 向量数据库

**向量数据库（Vector Database）**用于存储向量及相关数据，并根据向量相似度寻找内容接近的记录。它常用于 RAG 的语义检索。

例如，用户搜索“如何取消订单”，系统可以找到内容中使用“撤销购买”或“关闭订单”的文档，即使措辞并不完全相同。

基本概念

  • Embedding（嵌入向量）：把文本、图片等内容转换成数值向量。
  • 相似度搜索：根据向量距离或相似度找出接近的内容。
  • Metadata（元数据）：文档标题、日期、权限、类别等可用于过滤的字段。

向量数据库不是完整的 RAG 系统。应用还需要负责文档处理、检索策略、Prompt 组织、模型调用和权限控制。小型应用也可以先使用普通数据库或本地向量索引。

5. Agent

**Agent（智能体）**是能够根据目标决定下一步行动，并通过工具与外部系统交互的模型应用。

  • 搜索知识库。
  • 查询订单或库存。
  • 调用计算程序。
  • 创建工单或发送通知。

Agent 的重点不只是“模型会思考”，而是模型可以在程序设定的边界内选择工具和步骤。涉及付款、删除、发信等高影响操作时，通常需要权限控制、确认步骤和审计记录。

6. LangChain

LangChain 是用于搭建 LLM 应用的开发框架，提供组织模型调用、Prompt、检索器、工具和工作流的组件。

它常用于：

  • 构造 Prompt 并调用模型。
  • 建立文档加载、切分和检索流程。
  • 连接向量数据库。
  • 让模型调用外部工具。
  • 编排多步骤任务。

框架可以减少集成工作，但并非每个应用都需要。简单功能可以直接调用模型服务的 SDK；当应用组件增多、需要切换模型或管理复杂流程时，再评估是否引入 LangChain 等框架。

7. 主流技术之间的关系

这些技术可以组合使用，但不是每个应用都需要全部采用。应根据任务复杂度、资料来源、准确性要求和维护成本选择方案。

8. AI 能力落地业务场景

客服知识助手

  • 用户提出问题。
  • RAG 从产品说明和客服知识库检索资料。
  • LLM 根据检索内容组织回答，并附上来源。
  • 低置信度或高风险问题转人工。

销售与市场内容辅助

  • 输入产品信息和目标受众。
  • Prompt 约束文案风格、长度和渠道。
  • 模型生成邮件、商品描述或社交媒体草稿。
  • 工作人员审核后发布。

文档处理与信息抽取

  • 从合同、申请表或反馈中提取字段。
  • 按结构化格式返回结果。
  • 程序检查字段类型、必填项和取值范围。
  • 不确定或异常记录交由人工复核。

开发团队知识查询

  • 将技术文档、设计决策和代码说明整理进知识库。
  • 用 RAG 检索相关内容。
  • 模型总结资料并给出文档出处或链接。

业务流程自动化

  • Agent 查询订单、检查规则并生成处理建议。
  • 程序执行明确授权的操作。
  • 涉及资金、账户或不可逆操作时，增加人工确认。

场景选择时要评估

  • 任务是否经常发生、是否耗时？
  • 模型错误会造成多大影响？
  • 是否有可靠资料或可验证的标准答案？
  • 哪些环节必须人工审批？
  • 是否能衡量节省的时间、准确率或用户满意度？

9. AI 辅助开发工具

AI 辅助开发工具可以帮助开发者：

  • 解释代码、生成代码草稿。
  • 根据需求补充测试用例。
  • 分析错误信息和定位问题。
  • 重构代码、生成注释或文档。
  • 在 IDE 或终端中协助完成多步骤开发任务。

使用时应把 AI 产出视为待审查的建议。特别要检查代码是否符合项目约定、是否处理边界情况、是否引入安全问题，以及是否真的运行通过。

10. AI 辅助开发流程

一个较可靠的协作流程是：

  1. 明确需求：说明目标、输入输出、限制和验收标准。
  2. 提供上下文：给出相关代码、接口、错误信息和项目约定。
  3. 拆分任务：先让 AI 分析方案，再逐步实现较小改动。
  4. 检查差异：阅读 AI 修改的每个文件，确认改动范围和逻辑。
  5. 运行验证：执行项目已有的测试、构建或手动验证。
  6. 根据结果迭代：把失败现象和具体输出反馈给 AI。
  7. 整理交付：确认文档、错误处理和使用方式与实际实现一致。

注意点

  • 给出可验证的目标。
  • 避免一次要求 AI 修改过多不相关部分。
  • 不要把密钥、个人数据或敏感业务信息直接交给不适合处理这些数据的工具。
  • 对数据库迁移、部署、删除数据等高影响操作，仔细审查步骤和影响范围。
  • 最终责任仍由开发者承担：代码需要检查和验证。

LLM 应用开发的核心，是把模型能力与业务数据、检索、工具和验证流程连接起来，并在效率、准确性、安全性和维护成本之间做取舍。
