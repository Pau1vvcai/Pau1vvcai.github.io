Week 1: Introduction

What Are ML Systems?

Machine Learning Systems (ML Systems) studies how to train, run, and deploy machine learning models efficiently on real hardware and software systems. It considers more than the model itself: algorithms, compilers, GPUs, memory, communication, and networks all affect performance.

A model that is mathematically valid may still be inefficient to run. The central challenge in ML Systems is to make models run faster and use fewer resources under limited compute, memory, and communication capacity.

Major Areas of ML Systems

  • ML Models: Model architectures, parameters, and training methods.
  • Algorithmic Optimization: Changes to a model or algorithm that reduce cost while preserving as much model quality as possible.
    • Pruning: Removes unimportant weights, neurons, or modules.
    • Quantization: Uses lower-precision representations for weights or computations to reduce memory use and computation.
    • Sparsity: Increases the number of zero-valued parameters or intermediate values. Whether hardware can exploit sparsity efficiently depends on the implementation.
    • Low-rank approximation: Approximates a matrix with smaller matrices or factors to reduce computation and storage.
    • Fine-tuning: Continues training a pretrained model so it can adapt to a new task or dataset.
    • Mixture of Experts (MoE): Uses a routing mechanism to select a subset of experts for each input. The model can have many parameters overall while activating only some of them for each input.
    • Retrieval-Augmented Generation (RAG): Retrieves external information before generating a response and provides the retrieved material as context to the model.
  • Graph-Level Optimization: Transforms operations and dependencies in a computation graph, for example through algebraic simplification, fusion, or reordering.
    • Algebraic transformations: Rewrite computations using mathematical identities.
    • Partially equivalent transformations: Are equivalent only when certain conditions hold; those conditions must be checked.
    • Superoptimization: Searches for a more efficient implementation among equivalent alternatives.
  • Parallelization and Distributed Training: Distributes computation across multiple GPUs or machines.
    • Includes data parallelism, model parallelism, pipeline parallelism, and automated parallelization.
  • ML Compilation: Converts model computations into programs suited to the target hardware.
    • Tile-based ML compilers: Divide computations into hardware-friendly blocks, or tiles.
    • Learning- or search-based optimization: Uses search or learning to find more efficient implementation configurations.
  • Memory Optimization: Reduces memory usage during training or inference.
    • Rematerialization (activation recomputation): Recomputes intermediate results when needed instead of saving them, trading extra computation for lower memory use.
    • Zero redundancy: Shards training state that would otherwise be redundantly stored across devices.
  • Kernel Programming: Writes low-level, efficient GPU programs.
    • Includes modern GPU architectures, CUDA, warp specialization, and persistent kernels.
  • Network: Multi-GPU and multi-machine training relies on networks to transfer parameters, gradients, and activations. Network performance affects end-to-end efficiency.

The course aims to help students:

  1. Understand the major components of modern machine learning frameworks.

Week 1: How to Read a Paper

Assigned reading: How to Read a Paper

The Three-Pass Approach

Pass 1: Build a high-level understanding

The goal is to understand what the paper is about and whether it merits closer reading. Try to answer:

  1. Category: What kind of paper is it? For example, is it a measurement paper, an analysis of an existing system, or a description of a research prototype?
  2. Context: Which papers is it related to? What theoretical foundations or prior methods does it use?
  3. Correctness: Do the assumptions appear reasonable? Does the evidence support the claims?
  4. Contributions: What are the paper’s main contributions?
  5. Clarity: Is the paper clearly written?

Pass 2: Examine the important details

  1. Study the figures, diagrams, and other illustrations carefully to understand the system components and how they relate.
  2. Mark related papers and references that may be worth reading.
  3. Note key terminology, experimental settings, baselines, and main results.

Pass 3: Develop a deep understanding and consider reproduction

  1. Try to “virtually reimplement” the paper: What are the inputs, what is the processing pipeline, and what is the key algorithm?
  2. Identify the assumptions, parameters, and hardware needed to reproduce the results.
  3. Think about how you would explain the paper’s central idea to someone else.
  4. Note the paper’s limitations and possible directions for future work.

What to Take Away from a Paper

After reading a paper, you should be able to explain in a few sentences:

  • What problem does it address?
  • Why are existing methods insufficient?
  • What is its core method or system design?
  • How do the experiments validate it?
  • What are its costs, limitations, and intended use cases?

Week 2: Introduction to ML Systems

Deep Neural Networks

A Deep Neural Network (DNN) consists of many trainable mathematical units that work together to learn complex input-output mappings.

Training a DNN typically requires many matrix operations, storage for intermediate activations, and updates to model parameters. As a result, training performance depends not only on the algorithm but also on GPU compute, memory capacity, and communication between devices.

Stochastic Gradient Descent (SGD)

Model training typically repeats the following steps:

  1. Forward propagation: Feed a batch of input samples through the model and compute predictions.
  2. Loss computation: Compare predictions with the target values to measure error.
  3. Backward propagation: Use the chain rule to compute gradients of the loss with respect to the model parameters.
  4. Weight update: Use an optimizer to update the parameters based on the gradients.

Your original notes summarize training in three stages. Loss computation is listed separately here to make its role between forward and backward propagation explicit.

A training step can be summarized as:

Input → Forward computation → Loss → Gradients → Parameter update

Parallel Training

Data Parallelism

In data parallelism, each device holds a copy of the model and processes a different portion of the data.

A typical workflow is:

  1. Split the training data into batches or sub-batches.
  2. Each GPU runs the same model on its own data.
  3. Each GPU performs forward and backward propagation.
  4. Aggregate gradients across GPUs, then synchronize the model parameters.

Advantage: Multiple GPUs can increase training throughput when the model fits on one GPU.
Cost: Each GPU stores a model copy, and gradient synchronization requires communication.

Model Parallelism

Model parallelism splits a model into parts and places those parts on different devices. It is useful when a model does not fit on one GPU or when computation needs to be distributed.

Pipeline Parallelism

Pipeline parallelism assigns different model layers to different GPUs and divides a batch into microbatches. Ideally, different GPUs process different microbatches at the same time.

Main challenge: Some devices may be idle while the pipeline starts up or drains. These idle periods are called pipeline bubbles. Microbatch scheduling affects both bubble overhead and memory use.

Tensor Parallelism

Tensor parallelism splits a large tensor operation—such as a matrix multiplication in a linear layer—across multiple GPUs. In a Transformer, tensor parallelism can be applied to attention and feed-forward layers.

Main challenge: Devices need to exchange partial results within a layer. Tensor parallelism is therefore sensitive to communication bandwidth and latency between GPUs.

3D Parallelism

LLM training often combines three forms of parallelism:

  • Data parallelism: Different devices process different data.
  • Tensor parallelism: Large matrix operations within a layer are split across devices.
  • Pipeline parallelism: Different model layers are placed on different devices.

This combination is commonly called 3D parallelism. Real systems may also use sequence parallelism, expert parallelism, and other methods.

Machine Learning Compilation

Core Concepts

  • Tensor: A multidimensional array that stores model inputs, outputs, parameters, and intermediate results.
  • Tensor function: Defines computations over tensors. A single tensor function can contain multiple operations.
  • Computation graph: A graph whose nodes represent operations and whose edges represent data dependencies.

Goals of ML Compilation

A machine learning computation can often be implemented in several equivalent ways. A compiler tries to find an implementation better suited to the target hardware. Common goals include:

  1. Reducing memory use.
  2. Reducing execution time.
  3. Increasing hardware utilization.

These goals can conflict. For example, rematerialization reduces memory use but increases computation. Operator fusion may reduce memory traffic but increase register pressure.

Graph-Level Optimizations

Graph-level optimization uses information about a wider region of computation to rewrite a program. Examples include:

  • Fusing adjacent operations to reduce intermediate tensors and memory traffic.
  • Eliminating redundant or unnecessary computations.
  • Reordering or reformulating computations.
  • Automatically searching for semantically equivalent implementations that run faster.

Automated discovery of graph optimizations uses search or other automated methods to explore possible graph transformations and evaluate their correctness and performance.

Memory Bottlenecks in Training

During training, GPU memory may need to store:

  • Model parameters: The trainable weights.
  • Gradients: A gradient for each parameter.
  • Optimizer state: For example, Adam stores momentum and second-moment estimates for each parameter.
  • Activations: Intermediate results from the forward pass that may be needed during backpropagation.
  • Temporary workspace: Buffers and temporary tensors used by operators.

The maximum model size that can be trained is therefore often limited by GPU memory. Larger models may improve predictive performance, but they also require more memory for parameters, activations, and optimizer state, as well as more communication.

Tensor Rematerialization

Saving every intermediate activation during training can consume a large amount of memory. Rematerialization saves only selected activations and recomputes others during backpropagation.

  • Benefit: Reduces activation memory.
  • Cost: Repeats some forward computation, increasing compute time.

Zero Redundancy

Parallel training can lead to redundant storage of state across GPUs:

  • Data parallelism typically replicates model parameters, gradients, and optimizer state on every GPU.
  • Model or pipeline parallelism may also replicate data needed for boundary or intermediate computations.

The core idea of zero redundancy is to shard parameters, gradients, and optimizer state across GPUs, then communicate or gather the required data when needed.

  • Benefit: Reduces the training state stored on each GPU.
  • Cost: Adds communication, synchronization, and data-gathering overhead.

Balancing Compute, Memory, and Communication

Training system design must consider three costs:

  • Compute cost: The amount and time of computation.
  • Memory cost: Space used by parameters, activations, and optimizer state.
  • Communication cost: Time and bandwidth required to transfer data between devices.

For example:

  • Rematerialization trades more computation for lower memory use.
  • Zero redundancy trades more communication for less redundant storage.
  • More aggressive parallelization may increase compute throughput but also add synchronization overhead.

PyTorch and TensorFlow

Both frameworks can be used to build and train machine learning models. Historically, they have emphasized different programming and execution models.

TensorFlow’s Graph Execution Model

Traditional TensorFlow workflows often build a computation graph first and execute it afterward.

Characteristics:

  • The graph can be analyzed globally for graph-level optimizations.
  • Deferred execution gives the framework an opportunity to inspect a larger region of computation before running it.
  • Separating graph construction from execution can make debugging more difficult.

PyTorch’s Imperative Programming Model

PyTorch traditionally uses eager execution, which behaves more like ordinary Python: tensor operations run as the code reaches them.

Characteristics:

  • Code is intuitive to write, debug, and prototype.
  • Earlier execution models provided less global information, making some whole-program optimizations harder to apply.

PyTorch 2.x

PyTorch 2.x introduced graph capture and compilation capabilities. These allow graph-level optimization while preserving a familiar eager programming experience.

The goal is to combine:

  • The usability of imperative programming.
  • The performance potential of graph-level optimization.

The actual speedup depends on the model, operators, hardware, and compilation settings. Compilation does not guarantee that every workload will run faster.

One-Sentence Summary

ML Systems is about making system-level tradeoffs among model quality, computation time, memory use, and communication between devices.

Week 3: GPU Architecture & CUDA Programming

This week covers the CUDA programming model and GPU execution architecture, using matrix multiplication and parallel reduction to introduce common optimization techniques.
References: CMU 15-779 Lecture 3 & 4: GPU Architecture & CUDA Programming · NVIDIA: An Even Easier Introduction to CUDA

1. CPU vs. GPU

CPUs and GPUs make different design tradeoffs for different workloads:

  • CPU: Typically has fewer, more powerful cores. It is well suited to complex control logic, branching, and tasks with strong sequential dependencies.
  • GPU: Has many execution units and is well suited to applying similar operations to large amounts of data, such as vector operations and matrix multiplication.
  • Heterogeneous computing: Combines the CPU and GPU. The CPU handles control and task orchestration, while the GPU performs large-scale data-parallel computation.

The phrase “lightweight GPU threads” describes CUDA’s programming and execution model. It does not mean GPU threads are free: thread count, register usage, shared memory, and scheduling resources still affect performance.

3. The CUDA Programming Model

CUDA is NVIDIA’s parallel computing platform and programming model. CUDA C++ lets programmers express GPU thread organization, memory access, and synchronization with a relatively low abstraction distance from the hardware.

Host and Device

  • Host: Usually refers to the CPU and the code that runs on it.
  • Device: Usually refers to the GPU and the code that runs on it.
  • __global__: Declares a kernel that runs on the device and can be launched from host code.
  • __device__: Declares a function that runs on the device, usually called by other device code.
  • __host__: Declares a function that runs on the host.

Grid, Block, and Thread

CUDA organizes a kernel launch hierarchically:

  • Thread: The basic execution unit for a kernel.
  • Block: A group of threads that can cooperate using shared memory and synchronize with one another.
  • Grid: All the blocks launched by one kernel call.

CUDA provides built-in variables that describe thread positions and launch dimensions:

Variable Meaning
gridDim The dimensions of the grid; how many blocks there are along each dimension
blockIdx The current block’s index within the grid
blockDim The number of threads per block along each dimension
threadIdx The current thread’s index within its block

These dimensions can be one-, two-, or three-dimensional. The common type for specifying them is dim3.

4. CUDA Memory Model

In the traditional CUDA memory model, host and device use distinct address spaces:

  • A kernel cannot directly use an ordinary host memory address.
  • The CPU cannot access device memory like a local CPU array.
  • Data is typically copied explicitly between host and device.

A common device-memory allocation and copy sequence looks like this:

Common Device-Side Memory Levels

Memory type Scope Typical use
Per-thread private state / registers One thread Temporary variables and accumulators
Shared memory Threads within one block Cooperation and data reuse
Global memory All threads Inputs, outputs, and large data structures
Constant / texture and other cached paths Depends on hardware and access pattern Specific read-only or spatial access patterns

Registers and shared memory are typically closer to the execution units and faster to access, but their capacity is limited. Global memory is larger, but has higher access latency and bandwidth costs. Performance often depends on how well data is reused and whether memory accesses can be coalesced.

CUDA features such as Unified Memory provide additional abstractions. Understanding traditional host/device data movement is still useful.

Typical CUDA Program Workflow

  1. Allocate and initialize input data on the host.
  2. Allocate memory for device data.
  3. Copy inputs from host to device.
  4. Launch a kernel.
  5. Wait for the required work to finish and check for execution errors.
  6. Copy results from device to host.
  7. Free allocated host and device resources.

6. Synchronization and Atomic Operations

__syncthreads()

__syncthreads() is a block-level barrier:

  • All threads in the block must reach the barrier before any of them continue.
  • It is commonly used after threads cooperatively load data into shared memory.
  • Threads in a block must reach the barrier consistently. If some threads skip it while others wait, the program may hang or behave incorrectly.

It is not a global barrier across the grid and cannot synchronize different blocks.

Kernel Boundaries and Synchronization

Blocks can execute in any order and may run concurrently. A normal CUDA kernel cannot assume synchronization between blocks. One common way to express a global dependency is to split the computation across multiple kernel launches: a later kernel uses results produced by an earlier one.

7. GPU Architecture and Execution

Streaming Multiprocessor (SM)

A GPU contains multiple Streaming Multiprocessors (SMs). Blocks are scheduled onto available SMs, and an SM can host multiple blocks concurrently if its resources allow.

Scheduling depends on resources such as:

  • Number of threads and warps
  • Register usage
  • Shared-memory usage
  • Available execution resources on the SM

Therefore, launching many blocks does not mean they all run simultaneously. Blocks are scheduled as SM resources become available.

Specific figures in the lecture—such as the maximum number of resident warps per SM or shared-memory capacity—describe particular GPU architectures. They are not fixed values for every NVIDIA GPU.

Warp

A warp is an execution and scheduling unit on NVIDIA GPUs. A modern NVIDIA warp typically consists of 32 threads.

Threads in a warp execute the same instruction stream on different data. Warps are an important link between CUDA’s programming model and the hardware execution model.

Branch Divergence

If threads within one warp take different branches, the hardware may need to execute each path separately while masking threads that are not active on that path. This can reduce effective parallelism and is called warp divergence.

GPU programs often aim for consistent control flow within each warp. A branch is not automatically inefficient; the important question is whether threads in the same warp take different paths and how much work each path requires.

9. Case Study 1: CUDA Matrix Multiplication

Compute:

C = A × B

If A has shape M × K and B has shape K × N, then:

C[i, j] = Σ(k = 0..K-1) A[i, k] × B[k, j]

Basic Version: One Output Element per Thread

Each thread computes one output element C[i, j] by iterating over k and accumulating products.

This maps easily to a two-dimensional thread grid. However, different threads may repeatedly load the same elements of A and B from global memory, resulting in limited data reuse.

Optimization 1: Multiple Outputs per Thread (Register Tiling)

Each thread computes a small output tile instead of a single element. It can keep partial inputs and accumulators in registers, increasing the amount of computation performed per load.

The tradeoff is higher register usage per thread. Excessive register usage can reduce the number of warps that reside on an SM at the same time.

Optimization 2: Block-Level Shared-Memory Tiling

Each block computes a tile of the output matrix:

  1. Threads in the block cooperatively load parts of A and B from global memory into shared memory.
  2. Call __syncthreads() to ensure the data is ready.
  3. Threads reuse the tiles for multiply-accumulate operations.
  4. Load the next tiles and continue until the accumulation is complete.

Main benefit: Reduces repeated accesses to slower global memory by increasing data reuse.

Matrix multiplication optimization usually requires balancing tile size, register use, shared-memory capacity, memory coalescing, and occupancy.

Reduction Across Blocks

Large arrays usually require multiple blocks. Each block first computes a partial result and writes it to global memory. A second kernel then reduces those partial results.

The reason is that a normal CUDA kernel has no global synchronization barrier between arbitrary blocks. A kernel boundary can serve as a global phase boundary.

Reduction Optimization Considerations

  • Consistent control flow: Reduce warp divergence.
  • Coalesced memory access: Have adjacent threads access adjacent addresses.
  • Fewer barriers: Synchronize only when there are cross-thread dependencies.
  • Multiple blocks: Use multiple SMs for large inputs.
  • Numerical precision: Floating-point addition is not strictly associative, so different reduction orders may produce slightly different results.

11. Tensor Cores

Tensor Cores are specialized NVIDIA GPU units for matrix operations, especially the matrix multiply-accumulate workloads common in deep learning.

They can greatly increase throughput for supported data types and matrix shapes. Effective use generally requires:

  • Supported data types and operation forms.
  • Suitable matrix dimensions and layouts.
  • Framework, library, or kernel support that selects an appropriate Tensor Core path.
  • Verification that the result meets precision requirements.

Tensor Cores are specialized for certain matrix computations; they do not replace general-purpose CUDA cores for all workloads.

12. Key Takeaways

  1. CUDA expresses parallel work using grids, blocks, and threads.
  2. A common one-dimensional thread index is blockIdx.x * blockDim.x + threadIdx.x.
  3. Host and device have different execution and memory locations; traditional workflows explicitly manage data transfer.
  4. Threads within a block can cooperate through shared memory and synchronize with __syncthreads().
  5. Ordinary CUDA blocks cannot assume an execution order or synchronize globally.
  6. A warp typically contains 32 threads; warp divergence can reduce effective execution efficiency.
  7. Coalesced access and data reuse can improve GPU memory efficiency.
  8. Common matrix-multiplication optimizations include register tiling and shared-memory tiling.
  9. Parallel reductions often compute block-level partial results, then combine them in a later kernel.
  10. Tensor Cores provide specialized hardware acceleration for supported matrix operations.
